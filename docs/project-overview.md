## What This Project Is and Why It Exists

The Network Security Training Platform is a fully web-based cybersecurity education system commissioned by AUSDAIS PTY LTD, a technology organisation based in Bundoora, Melbourne, Australia. The platform was conceived in direct response to a critical and well-documented gap in the Australian cybersecurity training landscape — the absence of an accessible, affordable, and genuinely effective training solution that serves the broader Australian workforce rather than only university students.

Australia's cybercrime problem is not going away. The Australian Cyber Security Centre recorded 76,000 cybercrime incidents in 2022 to 2023, representing a 23 percent increase from the previous reporting period, and that figure has continued to climb through 2024, 2025, and into 2026. The average cost of a single cyberattack on a small Australian business exceeds $46,000 — and that is only the direct financial cost, not accounting for reputational damage, data loss, or regulatory penalties. What makes this particularly troubling is that the vast majority of successful cyberattacks do not exploit sophisticated technical vulnerabilities. They exploit people. Phishing emails, weak passwords, social engineering, insider threats, and misconfigured access permissions account for the overwhelming majority of breaches in Australia and worldwide. The technology to defend against these attacks already exists and is widely deployed. What is consistently missing is the human knowledge and awareness to use it properly.

The existing solutions to this problem fail in three specific and well-evidenced ways. First, the highest-quality cybersecurity training environments — cyber ranges, which simulate real network infrastructure for hands-on defensive exercises — are prohibitively expensive to build, operate, and maintain. They require dedicated server infrastructure, expert technical staff, and ongoing capital investment that places them entirely out of reach for small and medium businesses, local government councils, schools, and individual learners. Only large corporations and federal government agencies can realistically afford them. Second, the more affordable online training platforms that do exist almost universally target university students. A business employee in regional Queensland, a local council IT administrator in Western Australia, or a small business owner in suburban Melbourne has essentially no platform designed specifically for their context, their level of existing knowledge, or the specific Australian threat environment they face. Third, and most critically from a pedagogical perspective, virtually all existing platforms communicate assessment results as a single percentage score. A learner who scores 55 percent on a quiz is told they failed. They are not told which specific concepts they misunderstood, why their particular answers were wrong, what the correct understanding should be, or which specific lessons they need to revisit before attempting the quiz again. This approach produces neither genuine learning nor meaningful behaviour change.

The Network Security Training Platform was built from the ground up to solve all three of these problems simultaneously. It is delivered entirely through a standard web browser at no cost to the end user, requiring no specialist hardware, no software installation, and no prior technical knowledge. It is designed to serve four distinct target user groups within a single unified system. And it incorporates the Adaptive Feedback Engine — the platform's most distinctive and technically innovative feature — which analyses every single incorrect quiz response and generates a completely personalised study plan for each individual learner based on their specific pattern of wrong answers.

## The Technology Stack in Detail — Every Tool and Why

**Python 3.12.4** is the primary programming language. Python was specified by the client as a requirement and is the industry standard for web application development in the Australian education and cybersecurity sectors. Version 3.12 specifically provides improved error messages, performance improvements over 3.11, and full compatibility with all required packages including Django 6.0, psycopg2-binary, and django-otp.

**Django 6.0.6** is the web framework. Django follows the Model-View-Template architectural pattern which keeps the entire application within one codebase — one set of models defining the database structure, one set of views handling business logic and HTTP requests, and one set of templates rendering the HTML pages that users see. Django was chosen over alternatives like Flask or FastAPI because it includes a comprehensive set of built-in features that are critical for this platform — an ORM that handles all database queries without raw SQL, a built-in user authentication system that can be extended for role-based access, CSRF protection middleware active by default on all form submissions, automatic template output escaping preventing XSS attacks, and a powerful administrative interface. Django 6.0 specifically introduces improved async support and enhanced security defaults.

**PostgreSQL 18** is the relational database management system. It stores every piece of data the platform generates — user accounts, training content, quiz results, wrong answers, progress records, and certificates. PostgreSQL was chosen over SQLite (Django's default) for production because it supports concurrent access by multiple users simultaneously, provides robust referential integrity enforcement across all 12 tables through foreign key constraints, offers advanced indexing and query optimisation for the ORM aggregation queries used in the dashboards, and is the industry standard for production Django applications. PostgreSQL 18 brings improved performance for concurrent workloads and enhanced JSON support.

**psycopg2-binary** is the Python adapter that connects Django to PostgreSQL. It translates Django ORM queries into PostgreSQL-compatible SQL and handles the database connection pooling. The binary version is used rather than the source version to avoid requiring PostgreSQL development headers on the deployment server.

**Bootstrap 5.3** is the frontend CSS and JavaScript framework. It provides a comprehensive grid system for responsive layout across desktop, tablet, and mobile, a complete set of UI components including cards, navigation bars, modals, progress bars, badges, alerts, and buttons, and a consistent visual design language that works across all modern browsers without additional CSS preprocessing. Bootstrap 5 specifically removes the jQuery dependency that Bootstrap 4 required, resulting in faster page load times and a cleaner JavaScript codebase.

**django-otp** is the library implementing two-factor authentication. It provides TOTP — Time-based One-Time Password — authentication compatible with standard authenticator apps including Google Authenticator, Microsoft Authenticator, and Authy. When a user logs in they must open their authenticator app and enter the six-digit code that rotates every 30 seconds. This significantly reduces the risk of account takeover even if a user's password is compromised.

**Pillow** is the Python imaging library used for handling image uploads through the Instructor CMS. When an instructor uploads a cover image for a training module or an embedded image within a lesson, Pillow validates the file format, resizes it to the required dimensions, and saves it to the server's media storage directory.

**TinyMCE** is the rich text editor integrated into the Instructor CMS for lesson content creation. It provides a Microsoft Word-like editing interface in the browser, allowing instructors to write and format lesson content with headings, bold and italic text, bullet points, numbered lists, embedded images, code blocks, and tables — all without any HTML knowledge. The formatted content is saved as sanitised HTML in the Lessons database table.

**python-decouple** is the environment variable management library. In production, sensitive configuration values — the Django SECRET_KEY, database credentials, SMTP email server credentials, and any API keys — must never be hard-coded in settings.py or committed to the GitHub repository. python-decouple reads these values from a .env file on the server, keeping them completely separate from the codebase. This is essential for both security and for the ability to have different configurations for development, staging, and production environments.

**ReportLab** is the Python library used to generate PDF certificates. When a student completes all six modules and passes all associated quizzes, ReportLab creates a professionally formatted PDF document containing the student's full name, a unique UUID verification code, the certificate issue date, the AUSDAIS PTY LTD name and seal, and a list of all six completed training modules. The PDF is generated server-side and saved to the media directory, with a download link provided to the student.

**UUID** is Python's built-in universally unique identifier module. Each certificate generated by the platform receives a UUID4 code — a randomly generated 128-bit number formatted as a 36-character string. This UUID serves as the certificate's verification code, allowing anyone to verify the authenticity of a certificate by checking the code against the platform's database.

**django-ratelimit** is the brute-force protection library. It applies rate limiting to the login and registration views, restricting any single IP address to a maximum of ten attempts per hour. Requests exceeding this limit receive a 429 Too Many Requests response and are blocked for the remainder of the hour. This protects user accounts from automated password guessing attacks.

**OWASP ZAP** — the Zed Attack Proxy — is the automated security testing tool that will be used in Sprint 5 to scan the deployed staging environment for vulnerabilities. ZAP performs active scanning, which means it actually sends attack payloads to the application and observes the responses, identifying SQL injection points, XSS vulnerabilities, broken authentication, insecure redirect handling, and dozens of other vulnerability classes. All medium and high severity findings will be documented and remediated before the platform moves to production deployment.

**pytest-django** is the testing framework used to write and execute the unit test suite in Sprint 6. It extends the standard pytest framework with Django-specific fixtures and utilities, allowing the test suite to set up a test database, make HTTP requests through the Django test client, test authentication and permission logic, verify that views return the correct HTTP status codes and template context, and check that models correctly enforce database constraints. The target is a minimum of 80 percent code coverage across all views, models, and forms.

**coverage.py** works alongside pytest-django to measure code coverage. After each test run it produces a detailed report showing exactly which lines of code were exercised by the test suite and which were not, allowing Khadka Shrees to identify gaps in test coverage and write additional tests to fill them.

**GitHub Actions** provides the CI/CD pipeline. A workflow file in the repository defines automated actions that run every time a pull request is submitted — the test suite runs automatically, and if any test fails the pull request cannot be merged until the failure is resolved. This ensures that broken code can never make it into the main branch.

**Gunicorn** — Green Unicorn — is the production Python WSGI server. When Django's built-in development server is not suitable for production use, Gunicorn handles the actual HTTP request processing in a production environment. It spawns multiple worker processes to handle concurrent requests and integrates with PythonAnywhere's hosting infrastructure.

**Whitenoise** is the static file serving middleware. In production, Django does not serve static files — CSS, JavaScript, images, and fonts — by itself. Whitenoise integrates into the Django middleware stack and serves these files efficiently directly from the application server, without needing a separate web server like Nginx. It also handles gzip compression and long-term browser caching of static assets automatically.

**PythonAnywhere** is the cloud hosting platform where the production application will be deployed. It was chosen because it provides free Python web hosting with PostgreSQL database support, one-click HTTPS certificate provisioning, a browser-based file manager and console for deployment management, and WSGI configuration through a simple web interface. Its free tier imposes CPU usage limits and a daily restart cycle, which is acceptable for the current project scope.

## The Six Training Modules in Detail

**Module 1 — Network Security Fundamentals** is the entry point for all learners regardless of their background. It establishes the foundational vocabulary and conceptual framework for everything that follows. Lessons cover the CIA Triad — Confidentiality, Integrity, and Availability — as the three core principles that underpin all information security decisions. They explain what a network actually is, how data travels across networks, what the most common attack vectors targeting Australian organisations look like, and why human error consistently represents the most critical vulnerability in any system. The simulation activity presents learners with a scenario of a newly hired employee at a fictitious Melbourne small business, asking them to assess the security posture of the business's network setup and identify the most significant risks. The quiz of ten questions tests conceptual understanding of CIA Triad definitions, attack vector identification, and basic network terminology.

**Module 2 — Recognising Cyber Threats** builds directly on Module 1 by introducing learners to the specific categories of threats they are most likely to encounter in the Australian context. Lessons cover malware types including viruses, worms, trojans, ransomware, and spyware, explaining how each type operates, how it spreads, and how it can be recognised. The module covers distributed denial of service attacks, explaining what they are, why Australian businesses are targeted, and what the early warning signs look like. Real Australian cases are used throughout — the Optus data breach, the Medibank Private ransomware attack, and the Australian Parliament House email hack are all analysed as case studies to ground the training in the actual threat environment learners operate in. The simulation activity asks learners to analyse a series of system alerts and network events and correctly classify each one as either a legitimate activity or a specific type of cyberattack.

**Module 3 — Phishing and Social Engineering** addresses what Bishop confirmed as the most consistently exploited vulnerability in any system — human susceptibility to deception. Lessons cover email phishing in all its forms including spear phishing targeting specific individuals, whaling targeting senior executives, and clone phishing using convincing replicas of legitimate communications. They cover smishing through SMS, vishing through phone calls, pretexting where an attacker creates a fabricated scenario to manipulate a target, and baiting using physical USB drives left in carparks. The simulation activity is the most interactive in the entire platform — it presents learners with a realistic email inbox containing a mix of legitimate emails and phishing attempts of varying sophistication, and asks them to correctly identify which are genuine and which are attacks, explaining their reasoning for each.

**Module 4 — Secure Communication Practices** moves from threat recognition to defensive behaviour. Lessons explain how encryption works in practical terms accessible to non-technical users, why HTTPS matters and how to verify it, how to create genuinely strong passwords that balance security with memorability, how to set up and use multi-factor authentication on the specific platforms most commonly used in Australian workplaces including Microsoft 365, Google Workspace, and banking apps. The module also covers secure file sharing, the risks of public Wi-Fi, and how to communicate sensitive information safely through encrypted messaging. The simulation activity walks learners through securing a fictitious employee's entire digital workspace — email, passwords, two-factor authentication — step by step.

**Module 5 — Firewall and Network Defence** introduces learners to the technical controls that protect network infrastructure, explained at a level appropriate for non-specialist employees. Lessons cover what firewalls are and how they work, the difference between hardware and software firewalls, how network segmentation isolates critical systems from general access, what a VPN is and when and why to use one, how to read and interpret basic network security alerts, and what patch management means and why it matters. The simulation activity presents learners with a network diagram of a fictitious Melbourne business and asks them to identify the security weaknesses in the current configuration and recommend specific changes to harden it.

**Module 6 — Incident Response** is the most advanced module and prepares learners for the reality that no security posture is perfect — breaches happen, and knowing how to respond effectively is as important as prevention. The six-phase incident response lifecycle — Preparation, Identification, Containment, Eradication, Recovery, and Lessons Learned — is taught in depth, mapped to real Australian regulatory requirements including mandatory data breach notification obligations under the Privacy Act 1988. The simulation activity is a branching narrative where learners are told their organisation has just discovered what appears to be a ransomware infection on a server at 7am on a Monday morning. Every decision they make — who to call first, whether to disconnect the server from the network, whether to pay the ransom demand, what to tell customers — branches into different outcomes, demonstrating the real consequences of good and poor incident response decisions.

## The Database — All 12 Tables in Full Detail

**Users** table stores the core account record for every registered user on the platform. Key fields include a unique integer ID as the primary key, the user's email address as the unique login identifier, a PBKDF2-hashed password string, a role field constrained to one of three values — Student, Instructor, or Administrator, a boolean is_verified flag that is set to True only after the user clicks the email verification link, and a date_joined timestamp. This table directly uses Django's built-in AbstractUser model extended with the role and verification fields.

**UserProfiles** table stores the extended profile information and gamification data associated with each user account. It has a one-to-one foreign key relationship with the Users table. Fields include the user's organisational affiliation as a text field, a profile avatar image field, a last_active datetime field updated on every login used to calculate login streaks and identify at-risk learners, a streak_count integer field, a points integer field accumulating 10 points per lesson completed and 50 points per quiz passed, and a JSON field storing the list of earned achievement badge identifiers.

**Modules** table stores the configuration record for each of the six training modules. Fields include a unique ID, the module title, a rich text description, a difficulty level field constrained to Beginner, Intermediate, or Advanced, an estimated duration in minutes, an order_index integer field determining the sequential lock order, an is_published boolean field controlling student visibility, and foreign key references to the instructor who created the module and the timestamps for creation and last modification.

**Lessons** table stores individual lesson records within each module. Each module has four lessons. Fields include a unique ID, a foreign key to the parent Module, a lesson_number integer field ordering lessons within the module, a title, a body_text field storing the full TinyMCE-formatted HTML lesson content, an estimated reading time in minutes, and a boolean is_active field. The body_text field uses Django's TextField to accommodate long-form lesson content of 800 words or more.

**Simulations** table stores the interactive simulation activity for each module — one simulation per module. Fields include a unique ID, a foreign key to the parent Module, a scenario_text field containing the introductory scenario description, a decision_points JSON field storing the branching decision structure for the simulation, and an outcome_text field for each possible outcome based on the learner's decisions.

**Quizzes** table stores the quiz configuration for each module — one quiz per module. Fields include a unique ID, a foreign key to the parent Module, a time_limit field in minutes set to 30, a pass_mark percentage field set to 70, and an is_active boolean controlling whether the quiz is available to students.

**Questions** table stores individual quiz questions. Each quiz has a question bank of more than ten questions allowing random selection. Fields include a unique ID, a foreign key to the parent Quiz, the question_text, a difficulty field, and an ordering field.

**Answers** table is the most important table for the Adaptive Feedback Engine. Every question has exactly four answer records — one for each option A through D. Fields include a unique ID, a foreign key to the parent Question, option_text for each answer option, a correct_answer boolean flag marking which option is correct, and critically the explanation_text field — a detailed paragraph written by Bigyap Ghimire explaining why this answer is correct or incorrect, which the Adaptive Feedback Engine retrieves and presents to the learner for every question they answered incorrectly.

**QuizResults** table stores one record for every quiz attempt by every student. Fields include a unique ID, a foreign key to the student's User record, a foreign key to the Quiz, the percentage score, a passed boolean, the attempt number indicating whether this is a first, second, or subsequent attempt, and a submitted_at timestamp.

**WrongAnswers** table stores one record for every incorrect response within every quiz attempt. This table is the data source for the Adaptive Feedback Engine. Fields include a unique ID, a foreign key to the QuizResult, a foreign key to the Question, the student_answer field recording which option the student chose, and the correct_answer field. By joining WrongAnswers with the Answers table the Adaptive Feedback Engine can retrieve the explanation text for every incorrect response in a single query.

**ProgressRecords** table stores one record for every lesson that a student completes. Fields include a unique ID, a foreign key to the Student user, a foreign key to the Lesson, and a completed_at timestamp. Module completion percentage is calculated in the Student Dashboard view by counting the number of ProgressRecord entries for a student within a module divided by the total number of lessons in that module.

**Certificates** table stores one record for every completion certificate issued. Fields include a unique ID, a foreign key to the Student user, a UUID4 code generated using Python's built-in uuid module as the certificate's unique verification identifier, an issued_at timestamp, and a pdf_path field storing the filesystem path to the generated PDF certificate file.

## The Six-Sprint BN304 Implementation Plan in Full Detail

### Sprint 1 — Weeks 13 and 14 — Environment Setup and Core Authentication

This sprint establishes the entire technical foundation of the project. Everything built in all subsequent sprints depends on what is built here being solid, secure, and well-structured.

The first task is configuring the Django project structure correctly. Rather than putting all code in a single Django app, the project is organised into four purpose-specific apps — authentication handling all user account logic, modules handling all training content and CMS logic, quizzes handling the quiz engine and adaptive feedback engine, and certificates handling PDF generation and certificate records. This separation keeps the codebase maintainable and allows each team member to work on their app without constantly conflicting with others in the same files.

The second task is creating all 12 PostgreSQL database tables using Django ORM migrations. Aashish Dhakal will write the model definitions for all 12 tables in the appropriate app's models.py file, and Django's migration framework will translate these Python class definitions into the SQL CREATE TABLE statements that set up the actual PostgreSQL database schema. Running python manage.py makemigrations followed by python manage.py migrate creates all tables with the correct field types, constraints, indexes, and foreign key relationships.

The third task is implementing the complete user registration system. The registration view collects first name, last name, email address, password, password confirmation, role selection, and organisational affiliation. On submission the view validates the form — checking email uniqueness, password strength using Django's built-in password validators, and confirming the two password fields match — creates the User and UserProfile records, sends an automated verification email using Django's EmailMessage class with a time-limited signed URL, and redirects to a confirmation page. The account remains inactive until the verification link is clicked.

The fourth task is implementing the login system with two-factor authentication. The login view validates credentials and on success checks whether the user has completed 2FA setup. If not, it redirects to the 2FA setup page where the user scans a QR code with their authenticator app. On subsequent logins after 2FA is configured, the user enters their TOTP code in a second step after password verification. The django-otp library handles all TOTP generation, verification, and QR code display.

The fifth task is implementing role-based access control. Django's built-in Group and Permission framework is used to create three groups — Students, Instructors, and Administrators. Each view across the entire platform is decorated with a permission check ensuring only users with the correct role can access it. For example the Instructor CMS views are decorated with @permission_required('modules.can_manage_content') and the Administrator Dashboard views with @login_required combined with a role check in the view logic.

The sixth task is setting up GitHub Actions CI. A workflow YAML file in the repository's .github/workflows directory defines a job that triggers on every pull request to the main branch — it installs all Python packages, sets up a test PostgreSQL database, runs the pytest-django test suite, and fails the pull request if any test fails.

### Sprint 2 — Weeks 15 and 16 — Training Modules and Content Management System

This sprint builds the content layer of the platform — the ability to create and manage training modules, and the ability for students to browse and enrol in them.

The Module model is built with all required fields and the order_index sequential lock logic. The Lesson model is built with a foreign key to Module and the TinyMCE body_text field. The Simulation model is built with the branching decision_points JSON structure.

The Instructor CMS is implemented using Django's class-based views. CreateView handles new module creation, UpdateView handles editing existing modules, and DeleteView handles soft deletion — setting is_published to False rather than actually deleting records, preserving historical quiz result data. All CMS views are decorated with the Instructor permission group requirement. TinyMCE is integrated by adding the django-tinymce package to INSTALLED_APPS and configuring the TinyMCE settings in settings.py to allow the full toolbar including image embedding and code blocks.

The Student module browser view uses Django ORM to query all published modules ordered by order_index, annotates each with the student's enrolment status and completion percentage calculated from their ProgressRecord count, and applies the sequential lock logic — a student can only access Module 2 after completing Module 1, Module 3 after Module 2, and so on. Bootstrap 5 card components display each module with a visual completion indicator and a lock icon for modules not yet accessible.

Bigyap Ghimire writes Modules 1 and 2 lesson content — four lessons each at a minimum of 800 words per lesson — and enters it through the Instructor CMS interface during this sprint.

### Sprint 3 — Weeks 17 and 18 — Quiz Engine and Adaptive Feedback Engine

This is the most technically complex sprint and contains the platform's primary innovation.

The Quiz Engine is implemented as follows. The QuizAttempt view uses Django ORM to randomly select 10 questions from the question bank for the relevant module using Python's random.sample function applied to a queryset. Each question is rendered with its four answer options in a Bootstrap 5 form. A JavaScript countdown timer running in the browser counts down from 30 minutes and submits the form automatically if the time expires. Each answer the student selects is stored in Django's session object so that a page refresh does not lose previous answers. On final submission the view iterates all submitted answers, retrieves the correct_answer flag from the Answers table for each question, calculates the number of correct responses, divides by 10 to get the percentage score, compares against the 70 percent pass mark, creates a QuizResult record, and for every incorrect response creates a WrongAnswer record with both the student's chosen answer and the correct answer.

The Adaptive Feedback Engine is implemented as a function called after every quiz submission. It takes the QuizResult record as input and performs the following operations. It queries all WrongAnswer records associated with that quiz result. For each wrong answer it performs a JOIN query to the Answers table to retrieve the explanation_text for both the student's wrong answer and the correct answer. It queries the Lessons table to retrieve the specific lesson most closely associated with each wrong answer's topic area, determined by a lesson_reference foreign key field on the Question model. It groups the wrong answers by module section — for example all phishing-related wrong answers are grouped together, all CIA Triad related wrong answers are grouped together. For each group it calculates an estimated revision time by multiplying the number of wrong answers in the group by the average reading time of the associated lessons. It then renders the results page using a Django template that displays the personalised feedback report and the prioritised study plan.

### Sprint 4 — Weeks 19 and 20 — Dashboards and Progress Tracking

The Student Dashboard view uses Django ORM aggregation to calculate all displayed statistics in a single database query where possible. The Count aggregation counts completed modules, the Avg aggregation calculates average quiz score across all attempts, and annotation on the queryset adds the completion percentage for each module. Points are calculated by counting ProgressRecord entries multiplied by 10 plus QuizResult pass records multiplied by 50. The login streak is calculated by comparing the last_active datetime in UserProfile against today's date on every login and incrementing or resetting the streak counter accordingly.

The achievement badge system defines badge criteria as a dictionary in the badges.py utility file. Each badge has an identifier, a display name, an icon, and a condition function that takes a student's statistics as input and returns True if the criteria are met. The awarding logic runs after every significant user action — lesson completion, quiz submission, and login — checking all unearned badges against the current statistics and creating badge records for any newly earned ones.

The Administrator Dashboard generates the user progress table using a complex ORM queryset that annotates every User record with their module completion count, last quiz score, and last active date. The CSV export uses Python's built-in csv module to write this data to a CSV file object that is returned as an HTTP response with the content-disposition header set to trigger a download.

### Sprint 5 — Weeks 21 and 22 — Certificate System and Security Hardening

Certificate generation is triggered automatically by a post-save signal on the QuizResult model. ## Security Architecture — Every Layer

At the **network level** all data transmission between user browsers and the PythonAnywhere server is encrypted using HTTPS with TLS 1.2 or higher. This prevents man-in-the-middle attacks and eavesdropping on login credentials, quiz responses, and personal data.

At the **application level** Django's CSRF protection middleware is active on every form submission across the entire platform. This means every form includes a hidden CSRF token field, and Django validates this token on every POST request. Any request without a valid token — which would indicate a cross-site request forgery attack — is rejected with a 403 Forbidden response.

At the **database level** all database queries use Django's ORM exclusively. The ORM parameterises all query inputs automatically, meaning user-supplied data is never concatenated directly into SQL strings. This completely prevents SQL injection attacks regardless of what input a user submits through any form field.

At the **template level** Django's template engine automatically escapes all output by default. Any user-supplied content rendered in a template — usernames, organisation names, lesson content, quiz question text — has all HTML special characters escaped before rendering. This prevents stored cross-site scripting attacks where malicious JavaScript could be injected through user input and executed in other users' browsers.

At the **authentication level** passwords are hashed using PBKDF2 with SHA256 and 260,000 iterations before storage. The number of iterations exceeds OWASP's current recommendations and means that even if the database is compromised, brute-forcing the passwords from the hashes would be computationally infeasible. Two-factor authentication through django-otp adds a second independent authentication factor that cannot be phished in the same way as passwords.

At the **rate limiting level** django-ratelimit applies a maximum of ten login and registration attempts per IP address per hour. Exceeding this limit results in a 429 Too Many Requests response and blocks all further attempts from that IP for the remainder of the hour, preventing automated credential stuffing and brute-force attacks.

At the **access control level** role-based permissions enforced at the view level ensure that a Student cannot access Instructor or Administrator views, an Instructor cannot access Administrator views, and an unauthenticated user cannot access any authenticated view. All sensitive views check permissions on every request rather than only at login, preventing privilege escalation through session manipulation.
